## チャンネルと受付の体験

2026-09-27追加指示: コマンドまたは先頭の`++バックログ追加`がある投稿のみ受付対象とする。普通の文章・人間の議論・引用中の命令は新規バックログにしない。受付後に作った確認スレッド内の返信は既存受付への補足として扱う。

チームの常設バックログ受付チャンネルと、スプリントごとの通常チャンネルを持つ。投稿先は管理者が登録・確認した場所に限定する。

1. バックログ投稿を受けたら原文への参照と受付IDを保存し、その投稿を親にスレッドを作る。
2. 親投稿へ「内容を確認し、このスレッドで不足情報を確認します。追記はスレッドにお願いします」と案内する。
3. 目的・背景、求める変更、対象・範囲、完了条件を確認する。矛盾、曖昧な表現、過大な粒度、既存バックログとの重複候補、依存関係、期限の根拠を検討する。
4. 質問は不足理由と必要な追加情報を具体的に示し、同じ質問を重ねない。担当・期限・優先度・見積の未指定値は捏造しない。スプリント投入までに必要な項目と、受付時点で未定でよい項目を区別する。
5. 返信と編集を同じ受付IDに集約して再確認する。原文、整理案、判断理由を分離し、ユーザーに確認可能な形で提示する。
6. 情報が不足するものは受付済み・確認待ちとしてWebにも表示し、実装可能なバックログと区別する。内容確認後、権限を持つ人が登録内容を確定する。重複候補を理由に自動削除・自動完了しない。

状態案: received → checking → needs_information / needs_review → ready → registered。取消は履歴を保持する。外部メッセージIDと受付IDで重複を排除し、追記から別タスクを勝手に作らない。

内容の妥当性評価は根拠と質問を返す交換可能な審査インターフェースに分離する。Cc配備はCc側の審査キュー、独立配備は設定済みのLLM提供元を使う。未設定・失敗時は内容審査未実施を明示し、人間確認待ちにする。形式チェックだけを妥当性確認済みと呼ばない。モデルに承認・コード実行・チーム権限の決定を委ねない。

## スプリントの進行と投稿

- 目標・期間・タスク一覧を確認して計画を承認すると、スプリント用チャンネルと概要投稿を作成する。
- 実装フェーズではタスクの状態・関連成果・差し戻しを投稿に反映する。Ccがある場合は既存実行経路へ実装を委託できるが、独立配備はWeb/Botから人間が進捗・成果を登録できる。Cc runの終了をタスク完了と同一視しない。
- レビューは成果・受入条件・証跡、評価は目標への到達と判断理由、振り返りは良かった点・課題・次の改善を残す。未確認と確認済みを区別する。
- 既存のフェーズ承認・差し戻し・保留・再提出を再利用する。古い版の判断、匿名・未連携者の判断、Botによる人間承認の代行は拒否する。
- 議題別スレッドを同じスプリントのチャンネル配下に作り、Web側からタスク・レビュー・振り返りへ往復できる。

## 毎朝のスプリントサマリ

チームごとの時刻・IANAタイムゾーンを設定可能にする。初期提案は毎日09:00、Asia/Tokyo。実際の投稿開始は宛先設定と有効化後。

内容は目標、期間と締め切り、タスク一覧（状態・担当・個別期限）、未完了・遅延・確認待ち、Webへの導線。未設定は未設定と表示し、長い一覧は順序を保って分割投稿する。活動中のスプリントがない場合は常設チャンネルへその旨と計画待ちを表示する。

実行時計はActioが所有する。team/sprint/local-date/summary-kind/destinationを一意キーとした永続送信箱、排他実行、再起動復旧を使う。同日遅延起動は未送信分を一回送信し、過去日を大量送信しない。応答喪失はunknownとして投稿ID/外部照合キーで確認し、盲目的にPOSTし直さない。失敗は接続・操作別に表示する。

## アーカイブとWebログ

受入・評価・振り返りが確定し、未完了タスクの扱いも明示された終了スプリントを対象とする。期限到来だけでは閉じない。

ログの取込完了 → 最終サマリ → 日次投稿停止 → チャンネル保管の順で、各段階の結果を永続化する。ログ取込の欠落・配送不明・処理失敗時はarchive_pendingを表示し、アーカイブ完了と偽らない。

- Discord: 通常テキストチャンネルの投稿・スレッド作成を管理対象の一般参加者に対して停止し、既存スレッドをロック/アーカイブして保管カテゴリへ移す。閲覧権限は拡大しない。Discord管理者権限の例外は表示する。カテゴリ上限時は失敗理由を示し、削除へ切り替えない。
- Slack: Cc経由で対応APIのアーカイブを行う。
- チャンネルを削除しない。通常運用で終了済みを勝手に再開しない。

Actio Webにはチーム別の会話一覧、受付スレッド、スプリント別ログ、時系列表示、ページング、検索、元投稿へのリンクを設ける。編集・削除イベント、添付メタデータ、投稿/受信時刻、取込範囲・欠落を扱う。外部から削除された本文を通常閲覧に残し続けない。添付ファイルはまずリンクと取得可否を表示し、ファイルを勝手に複製しない。

Webログの権限は対応チームに加えて接続先チャンネルの公開範囲を尊重する。非公開スレッドをチーム全員へ公開しない。対応できない非公開面は設定時に明示的に拒否する。Ccを停止しても保存済みログを閲覧できる。

## 認証・設定・永続化

Discord Botの登録は管理画面から接続先・Botアプリ識別子・シークレット参照・対象チャンネル・権限状態を管理する。秘密値は既存の暗号化配備設定へ保持し、通常のActioテーブルやログ・API応答へ出さない。ユーザー本人の連携とチーム役割は既存Cernere/Actio境界を維持する。Cc不要はCcへの依存解消であり、既存の本人確認を省略する意味ではない。

会話ログは投稿内容と業務上の参照を保存し、投稿者の表示名・プロフィール・外部ユーザーIDの独自複製を避ける。本人解決できない投稿は権限操作へ進めず、登録内容確認用の未連携状態を表示する。自然文の受信に必要なBot権限/Message Content Intentが不足すればセットアップに表示する。

保存領域案: chat_connections、chat_surfaces、chat_messages、backlog_intakes、intake_reviews、chat_inbox、chat_outbox、sprint_summary_schedules。既存gate/outboxとの責務重複を避け、操作ID・source revision・本文hash・配送結果を保持する。SQLite/PostgreSQLに同じ契約を提供し、MySQLは既存計画機能と同じ未対応表示。

業務ロジック、審査提供元、配送契約、Ccアダプタ、Discordアダプタ、会話ログ、スケジューラ、ルート、画面を分割する。ネットワーク処理をDBトランザクション内に置かない。

## 実装範囲と順序

1. Actio: 独立チーム/プロジェクト登録、接続設定、provider-neutralな受信・配送・ログの契約と永続化。
2. Actio: バックログ受付と内容審査、スレッドでの質問/補足/確定、対応Web画面。
3. Actio + Cc: 既存gateを活かした通常チャンネルのスプリント進行、CcのDiscord/Slack対応、直接Discord Bot対応。
4. Actio: 日次サマリ、アーカイブ処理、Webログと復旧表示。
5. 重複受信・応答喪失・権限・再起動復旧・Ccなしの受入ケースを登録し、Revisorへ提出。実際のサービス操作・投稿・動作テストは所定の別許可/claim手順に従う。

旧フォーラムは一括移動・削除しない。新規運用から通常チャンネルを使い、既存スプリントの移行が必要な場合はID対応・ログ継承を確認した明示操作とする。

## 受入条件

1. Cc接続設定がなくてもチーム作成から投稿受付・質問・登録確定・スプリント運営・朝投稿・終了保管・Web閲覧まで到達できる。
2. Cc構成ではActioがDiscord/Slackへ直接送信せず、Cc経由で同じ体験になる。
3. 曖昧な投稿に具体的な質問スレッドができ、補足が同じ受付に反映される。権限確認前や情報不足のまま実装を開始しない。
4. 通常チャンネルを使用し、フォーラムを新規作成しない。
5. 朝投稿は設定時刻とタイムゾーンを守り、目標・一覧・期限を欠落させず、再起動で重複しない。
6. レビュー/評価/振り返りと人間の明示判断が記録され、終了条件成立後にのみ保管する。
7. アーカイブ後もWebで権限に応じた会話ログを参照でき、欠落・削除・配送失敗を区別できる。
8. 既存チーム、既存スプリント、Cc taskflow、一時登録の振る舞いを壊さない。
